# ADR003: Shared documents and runtime for level editing

- **Status:** Accepted for the editor MVP
- **Date:** 2026-09-20
- **Deciders:** Astra implementation decision under Tom's autonomous MVP authorization
- **Related requirements:** PRD002 R-01–R-10; DESIGN016

## Context

The shipped game already resolves versioned authored course documents into shared collision and placement data. Tom wants humans and inexpensive agents to assemble comparable worlds and obbys, reserving expensive development for art and mechanics. Duplicating game rules inside an editor or allowing generated scripts would undermine parity and increase review cost.

## Decision

Use a portable project envelope around the two authored chapter documents. Keep published route documents immutable. A single pure command layer and the existing structural/geometry validators serve both the visual editor and a CLI. The editor may retain structurally safe but semantically invalid drafts so authors can repair disconnected or unsupported placements; validation errors identify the offending object/path. Preview accepts only a complete valid project.

The browser provides local draft persistence, undo/redo and JSON interchange. This bounded MVP does not add shared server-side draft ownership before parent/admission contracts exist. Clearly identify browser-local storage and offer export even when storage fails. Import and command input are bounded data, never executable expressions or arbitrary resource URLs.

Preview freezes a validated snapshot and uses the same gameplay runtime and action rules as the shipped fictional playtest. The snapshot must travel with its isolated preview state so rendering, collisions, boss logic, retry, memory recovery and chapter transitions resolve the same placements. Never register mutable project data in the global published-route cache. Preview endpoints are restricted to the existing isolated fixture mode and retain session/origin/body-size protections.

The visual viewport is an editing aid, with standard 3D selection and transform controls. Playtest is the authority for actual artwork, camera and mechanics. Existing themed scenery remains generated by the runtime; new scenery asset production and generalized encounter mechanics are separate work.

## Alternatives

A forked editor engine duplicates behavior and weakens parity. Code generation as the primary authoring interface requires expensive reviews for ordinary layout edits. A full multi-user hosted publishing system adds identity, revision and media decisions that are unnecessary for testing layout authoring. Directly editing built-in route files would silently change existing adventures. The shared-document approach preserves a later path to revisioned publishing without requiring it for this MVP.

## Consequences

| ID | Consequence |
| --- | --- |
| C-01 | The same exported project can be edited by a human or agent and validated before play. |
| C-02 | Known roster and progression constraints remain explicit. Supporting new counts or mechanics needs a later contract change. |
| C-03 | Local storage is convenient but not a backup. JSON export is the portable artifact; failures must be visible. |
| C-04 | Preview requires coherent snapshot propagation across client/server boundaries and tests for concurrent isolation. |
| C-05 | Semantic invalidity blocks preview, not continued editing or exporting a repairable draft. |
